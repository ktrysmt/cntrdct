# ラベリング・ルーブリック v0 - Phase 0 単独評価者パイロット

Author: ktrysmt
Date: 2026-05-04
Project: cntrdct Track A (crates.io 上位 N 件の実証研究)
Status: `data/phase0/labelling.csv` のいかなる finding も評価する前に事前登録済み。
コミット時点で凍結し、以後の修正は差分付き v1 ファイルとして作成する。

## 1. この文書の目的

Phase 0 は単一の人間評価者（プロジェクト著者）によって評価される。
明文化されたルーブリックがない場合、79 件の finding 全体で暗黙の判断基準が
徐々にずれていく。すなわち、初期の判定は厳しく、後半の判定は緩くなり、
パイロットで報告される TP 率は再現不能になる。このルーブリックは、
いかなるラベル付けより前に判定規則を固定することで、次を担保する。

- 同一 finding には、最初に見ても 79 件目に見ても同じラベルが付く。
- Phase 1 で追加される第 2 評価者が同一の定義から開始できる。
- 最終論文の査読者がオフラインで判断を再現できる。

TP 側へ寄る単独評価者の確証バイアスは、この phase の既知の限界であり、
§6 に記載する。

## 2. 入力と出力

- 入力: `data/phase0/labelling.csv`（79 行。`labelling.json` から
  `scripts/phase0/build_labelling_csv.py` で生成）
- 評価作業中のファイル: `data/phase0/labelling-rated.csv`
  （入力のコピーに `label`、`rubric_clause`、`notes` 列を記入したもの）
- 最終出力: 本ルーブリックと同時にコミットされた
  `data/phase0/labelling-rated.csv`、および検出器ごとの
  TP / FP / Uncertain 件数を要約した短い Markdown

評価中、評価者は `RankedFinding` JSON、`cntrdct scan` の出力である
`findings.json`、および検出器の元ソースコードを開かない。評価世界は CSV のみとする。

## 3. ラベル値

| Label | 意味 | 使用条件 |
|---|---|---|
| `TP` | 真陽性 | このコードに関する検出器の主張が正しい。主位置に実在する欠陥、コードスメル、または修正に値する不整合がある。 |
| `FP` | 偽陽性 | 検出器の主張が誤り。コードは意図的・慣用的であるか、検出器が偶然の一致をパターン検出しただけである。 |
| `Uncertain` | 時間内に判定不能 | 抜粋だけでは判定できない、または TP/FP の両方が妥当と評価者が判断した場合。 |

大文字小文字は厳密に区別する。下流の集計は完全一致文字列で grep する。

## 4. 判定プロトコル（各 finding 共通）

1. `primary_excerpt` を読む（`>` で示された行を含め、上から順に読む）。
2. finding に `related_excerpts` があれば読む。
3. §5 の検出器別ルーブリックを適用する（該当検出器へ移動）。
4. `TP`、`FP`、`Uncertain` を選ぶ。該当する条項 ID
   （例: `TP-2`、`FP-1`、`U-3`）を `rubric_clause` 列に記入する。
5. 任意で自由記述 `notes` を記入する（1 行以内。同様ケースを
   Phase 1 評価者が扱う際に有用な情報）。
6. 保存し、次の finding に進む。

時間予算: finding 1 件あたり 60 秒。60 秒時点で未決なら
`Uncertain` とし、条項は `U-time` を記録する。超過しない。

同点時の扱い: TP と FP が同程度に妥当で決めきれない場合、
条項 `U-tie` で `Uncertain` とする。無理な二値化は精度推定のノイズ床を増やす。

評価順序: `labelling.csv` の行順で評価する
（すでに `detector_id`、次に `rank_score` 降順で整列済み）。
飛ばして先に進まない。再読が必要な finding はいったん `Uncertain` にし、
全件一巡後に再訪する。

## 5. 検出器別ルーブリック

### 5.1 clone-drift

検出器の主張: 主対象関数が N 個の近似クローン兄弟関数から乖離している。
この乖離は、グループ内のいずれかが不整合に編集されたこと
（バグ混入またはリファクタ残差のドリフト）を示す可能性がある。
または、乖離した 1 件のみが正しい実装である可能性がある。

TP-1 - 次の 3 条件をすべて満たす:

- 主対象と少なくとも 1 つの関連対象が、見て同一意図と判断できる
  （同じ setter 形、同じ trait メソッド、同じアルゴリズム段階、同じパース処理）
- ドリフトが観測可能な振る舞いに影響する
  （バリデーション有無、戻り経路の網羅、副作用回数、エラー処理形、
  早期 return 条件、off-by-one、符号、引数順）
- ドリフトが、意図的な型・ライフタイム・feature gate・
  generic 制約差だけでは説明できない

TP-2 - getter/setter の近似クローングループで、1 つだけ他と異なる。
その差分を評価者が `notes` 1 行で説明できる。
例: 10 個の `set_*` メソッドがすべて `self.x = v;` だが、
1 つだけ他にないバリデーションを実行する。

FP-1 - 主対象と関連対象は構文形のみが類似している
（例: 両者とも短い `match` arm、短い `From` 実装）一方で、
本体の概念的役割は異なる。

FP-2 - ドリフトは型・generics・lifetime・`cfg` の差で完全に説明でき、
ロジック欠落はない。

FP-3 - ドリフトが doc comment、属性（`#[inline]`、`#[cold]`）、
可視性修飾子のみにある。実行本体は同一または自明な改名のみ。

FP-4 - 主対象または関連対象すべてが自動生成コード
（build.rs 出力、proc-macro 展開、derive 展開）。
`notes` に `auto-generated` と記載する。

U-1 - 判定に、提示抜粋を超えた周辺 crate（呼び出し元、trait 定義、
テスト期待値）の読解が必要。

U-2 - 関連グループが 10 件以上で、時間内にパターン検証できない。

U-3 - `unsafe`、`async`、`cfg` 条件分岐スコープが関与し、
それがドリフト説明になるか確信できない。

U-time - 60 秒経過しても確信ある判定に至らない。

U-tie - TP と FP が同程度に妥当。

### 5.2 comment-code

検出器の主張: 主位置近傍のコメントが主張する性質を、隣接コードが破っている。

TP-1 - コメントが振る舞いに関する具体的主張
（戻り値、panic、ミューテーション、計算量 O(n)、スレッド安全性、
非ブロッキング、非空保証など）を行っており、可視コードが抜粋範囲内で
その主張に明確に反している。

TP-2 - コメントが陳腐化している。
コード側で改名・削除済みの名前（関数、引数、フィールド、ファイル）を参照する、
または削除済みコード経路を記述している。

TP-3 - コメントが反転している。
例: 「成功時に true を返す」とあるのに、成功時にコードは `false` を返す。

FP-1 - コメントは可視コードより高抽象の意図・不変条件を述べている
（例: 関数全体意図と本体の 1 分岐）。両者は整合している。

FP-2 - コメントは TODO、FIXME、NOTE、XXX の将来作業メモであり、
現在挙動の主張ではない。

FP-3 - コメントは doctest（` ```rust ` ブロック）で、
見かけの不一致は doctest 内コードと実装本体の差である。
doctest は別実行されるため、矛盾とはみなさない。

FP-4 - コメントが他言語（日本語など）で、評価者が翻訳ニュアンス一致に確信を持てない。
`notes` に `non-English comment` と記載する。
（注意: 実際の TP を過小評価するリスクがあるため、迷う場合は Uncertain を優先する。）

U-1 - コメント主張が、抜粋に本体がない被呼び出し先に依存しており、
違反有無を検証できない。

U-time / U-tie - §5.1 に準ずる。

### 5.3 unreachable-after-terminator

検出器の主張: 発散終端（`return`、`panic!`、`break`、`continue`、
`unreachable!`、`loop {}`、`process::exit`）の後続コードは到達不能である。

TP-1 - 終端後コードが、抜粋内で見えるいかなる実行条件でも実行不能。
rustc 自身が警告する水準。

TP-2 - 終端後コードが、論理的に不可能な構成でのみ実行される
（例: `if true { return; } else { ... }` の `else` が死んでいる）。

FP-1 - 終端が `cfg(...)` または feature flag で分岐されており、
「到達不能」コードは代替構成で実行される。

FP-2 - 終端がマクロ展開内部にあり、「到達不能」コードは設計どおりの
マクロ else 分岐である。

FP-3 - 見かけ上の終端が `loop { ... }` だが、本体に到達可能な `break` または
`return` を含む。loop は発散していない。

FP-4 - 終端後コードが同一制御フローブロックではなく、`match` の別 arm にある。

U-1 - `match` 網羅性または trait object dispatch により、到達可能性が
抜粋外コンテキストに依存する。

U-time / U-tie - §5.1 に準ずる。

### 5.4 arg-swap （Phase 0 で finding なし; ルーブリック草案）

上位 100 コーパスでは finding が発火しなかった。Phase 1（上位 1000）で
パターン顕在化が見込まれるため草案を保持する。概要:
- TP: 同一型 2 引数の渡し順が、呼び出し先シグネチャで見える引数名と矛盾する。
- FP: 引数型が異なる、または呼び出し側が位置的意味を意図的に用いている
  （例: `min(a, b)`）。

### 5.5 config-interaction （Phase 0 で finding なし; ルーブリック草案）

上位 100 コーパスでは finding が発火しなかった。Phase 1 向けに草案を保持する。
概要:
- TP: 相互排他的述語を持つ 2 つの `cfg` 属性が同一 item または兄弟 item に適用され、
  ある実行時構成で実装不在になる。
- FP: 述語は実際にはいかなる tier-1 target triple でも排他的ではない。

## 6. Phase 0 の限界

このルーブリックは単独評価者バイアスを除去しない。上限を与える:

- TP 側への確証バイアスは、評価者がプロジェクト著者であるため、
  最も支配的な残留リスクである。この pass で報告する精度値は
  楽観側上界として解釈する必要がある。
- rank_score / message によるアンカーバイアスは、CSV 上で当該列を右側へ移し、
  スプレッドシート表示で隠せるようにすることで緩和する。
  評価者は評価中にそれらを読まないことをコミットする。
- detector-id の漏洩は、ルーブリックが検出器依存である以上、不可避である。
  評価者は検出器メッセージではなくルーブリックを適用することが求められる。
- 79 行評価中の基準ドリフトは、自己整合性チェックで抑制する。
  全件終了後、評価者は id ∈ {1..10} を初回ラベル非表示で再評価し、
  1 回目/2 回目の一致率を脚注報告する。目標: 同一ラベル率 90% 以上。

Phase 1（上位 1000）では本ルーブリックを v1 で置き換え、次を必須とする:
- 独立な 2 名評価者
- 一致閾値として Cohen's κ >= 0.6
- 不一致時の調停プロトコル
- cntrdct プロジェクト非所属の評価者を 1 名含める

## 7. 凍結成果物

`labelling-rated.csv` のいずれか 1 行でも `label` が非空になった時点で、
本ルーブリックを凍結する。以後の規則変更は新規ファイル
（`2026-MM-DD-labelling-rubric-v1.md`）として作成し、
v0 規則が不十分だった理由を差分セクションで説明する。
v0 のラベル付き CSV は変更せず保存し、v0 規則由来バイアスを監査可能にする。
